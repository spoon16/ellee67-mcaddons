# Architecture

One behavior pack, one resource pack, one script bundle. Six features share them and can be
switched on and off per world.

## Where things live

```
behavior_packs/elleedog67/   the behavior pack, laid out exactly as Bedrock expects
resource_packs/elleedog67/   the resource pack, same rule
src/                         scripts; bundled by esbuild into dist/behavior_pack/scripts/main.js
test/                        vitest suites and the engine mock
tools/                       build, validate, package, version, codegen
docs/                        this folder
dist/                        build output (ignored by git)
```

Inside each pack, content is organised by Bedrock content type first (`entities/`, `items/`,
`attachables/` and so on, which the engine loads recursively) and by feature second:

```
behavior_packs/elleedog67/entities/stair-sit/seat.json
behavior_packs/elleedog67/items/redstone-guide/guide_book.json
resource_packs/elleedog67/render_controllers/pets/pet_armor.render_controllers.json
```

Two exceptions:

- Folders whose path is part of an identifier keep their original layout: `functions/<ns>/x.mcfunction`
  is `/function <ns>/x`, `structures/<ns>/x.mcstructure` is `<ns>:x`, and texture paths are
  referenced verbatim from JSON.
- Files that replace a vanilla definition (`minecraft:player`, `minecraft:enderman`, the player
  render controllers, the vanilla armor attachables) live under an `overrides/` folder so the
  risky files are visible at a glance. `npm run build` fails if a `minecraft:` identifier appears
  anywhere else.

Shared files that every feature contributes to are hand-maintained and organised in sections:
`texts/en_US.lang`, `texts/en_GB.lang`, `textures/item_texture.json`, `textures/terrain_texture.json`,
`blocks.json`.

Some folders are generated by `npm run codegen` and must not be edited by hand; see
[CODEGEN.md](CODEGEN.md). `.gitattributes` lists them.

## Scripts

`src/main.ts` calls `bootstrap(features)` with the list in `src/features/index.ts`. Each feature is
a folder under `src/features/<id>/` whose `index.ts` exports a `FeatureDefinition`:

```ts
interface FeatureDefinition {
  id: FeatureId;            // "pets" | "stair-sit" | "creeper-mod" | "ender-mod" | "redstone-guide" | "rbow-ore"
  title: string;            // "Stair Sitting"
  summary: string;          // one line for menus
  defaultEnabled: boolean;  // state for a world that has never toggled it
  disabledNote?: string;    // what keeps working while disabled (rbow-ore)
  register?(registries): void;   // startup: commands and item components, always runs
  alwaysOn?(ctx): void;          // after world load, regardless of the flag, never disposed (rare)
  start(ctx): void;              // subscribe events and intervals through ctx
  stop(ctx): void;               // restore vanilla-ish behaviour; ctx is disposed afterwards
}
```

The core (`src/core/`) provides:

- `features.ts`: the registry, `isEnabled`, `setEnabled`, `startFeature`, `stopFeature`. The
  enabled flag is a world dynamic property `elleedog67:feature:<id>`; when it is absent the
  feature's `defaultEnabled` applies.
- `subscriptions.ts`: `FeatureContext`, whose `on(signal, handler)`, `every(ticks, fn)`,
  `after(ticks, fn)` and `onDispose(fn)` are all undone by `dispose()`.
- `commands.ts`: `/elleedog67:enable`, `/elleedog67:disable`, `/elleedog67:features`,
  `/elleedog67:book`, plus the gated registries handed to `register()`. A gated command returns
  `CustomCommandStatus.Failure` with "X is disabled. An operator can run /elleedog67:enable x."
  while its feature is off; a gated item component's callbacks do nothing.
- `book.ts`: the ElleeDog 67 Book item, who receives it, and the toggle menu.

Bedrock cannot unregister commands or item components after startup, which is why
`register()` always runs and the gate lives in the callbacks.

## Lifecycle

1. `system.beforeEvents.startup` (early execution, no world access): core commands and the book
   component are registered, then every feature's `register()`. A throwing `register()` is logged
   and skipped; the others still run.
2. `world.afterEvents.worldLoad`: the core reads each feature's flag and calls `start(ctx)` for
   the enabled ones, then hands out books.
3. `/elleedog67:enable x`, `/elleedog67:disable x` or the book menu: on the next tick the flag is
   written and `start`/`stop` run. Command callbacks themselves are read-only in Bedrock, so all
   of this happens inside `system.run`.

`start()` must never subscribe to `worldLoad` (it already happened); do the load-time work
directly. A feature that needs to keep a small listener alive *while disabled* (Ender resets its
gate property on newly loaded Endermen, Pets forces native form on joining players) creates its
own `new FeatureContext(id)` inside `stop()`, keeps it in a module variable, and disposes it at
the top of `start()`.

## What "disabled" means per feature

| Feature | Disabled means | Stays in the world regardless |
|---|---|---|
| creeper-mod | vanilla creeper explosions | nothing |
| ender-mod | Endermen move blocks like vanilla; protection command refuses | the `minecraft:enderman` override (inert while the property is true) |
| stair-sit | seats and targets removed, sitting stops, `sit:*` commands refuse | nothing |
| redstone-guide | the guide book does nothing when used | the item and its recipe |
| rbow-ore | Rbow tool behaviours and legacy-drop recovery stop | ore generation, blocks, items, recipes; ore still drops (the drop handler is never gated) |
| pets | players return to native form, `pet:*` commands and the morpher refuse | the player override, items and recipe |

## Build

`npm run build` copies both pack folders to `dist/`, bundles `src/main.ts` with esbuild
(`es2020`, ESM, `@minecraft/server` and `@minecraft/server-ui` external) and runs
`tools/validate.ts`. `npm run package` zips `dist/` into `.mcpack` and `.mcaddon` files with fixed
timestamps so the same commit always produces the same bytes. Neither runs a generator.
